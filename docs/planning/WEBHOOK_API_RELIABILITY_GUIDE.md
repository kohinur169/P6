## ১. ওয়েবহুক গ্রহণের নিরাপত্তা ও নির্ভরযোগ্যতা

### ১.১ সিগনেচার ভেরিফিকেশন (বাধ্যতামূলক)
প্রতিটি ইনকামিং ওয়েবহুকের জন্য অনুরোধ শরীর (raw body) ন höhere প্রাধাননা দiat হবে। জেসন পার্স করার আগে সিগনেচার যাচাই করতে হবে।

**নিয়ম:**
- শপিফাই: `X-Shopify-Hmac-Sha256` হেডার, চাবি = `SHOPIFY_API_SECRET`
- ও stories: `X-KD-Signature` হেডার (হম্যাক-শা২৫৬), চাবি = এবং সার marchands-উল্লिखিত webhook secret
- পায়রোক: `X-Payroc-Signature` বা `X-Signature`, চাবি = `PAYROC_WEBHOOK_SECRET`
- মেভেরিক: `X-Maverick-Signature` বা `X-Signature`, চাবি = `MAVERICK_WEBHOOK_SECRET`
- অন্য প্রোভাইডার: তাদের ডকুমেন্টেশনেরpecified হেডার ও অ্যালগরিদম ব্যবহার করুন

**কোড উদাহরণ (টেমপ্লেট):**
```typescript
import crypto from 'crypto';

export function verifyHmacSha256(
  body: Buffer,
  signatureHeader: string | undefined,
  secret: string
): boolean {
  if (!signatureHeader || !secret) return false;
  const computed = crypto.createHmac('sha256', secret).update(body).digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(computed, 'utf8'),
    Buffer.from(signatureHeader, 'utf8')
  );
}
```

ভেরিফিকেশন ব্যর্থ হলে অবিলম্বে `401 Unauthorized` রিটার্ন করুন, ওয়েবহুক প্রসেস করবেন না।

### ১.২ আইডempootেন্সি (দ্বাভাবিক প্রসেস রোধ)
প্রতিটি ওয়েবহুকের একটি অনন্য ইভেন্ট আইডি থাকবে (যেমন: Shopify `X-Shopify-Event-Id`, পায়রոկ `external_event_id`, মেভেরিক `event_id`)।

**ডাটাবেস টেবিল:**
```sql
CREATE TABLE IF NOT EXISTS webhook_event_log (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    provider VARCHAR(32) NOT NULL,
    store_id UUID NOT NULL,
    external_event_id VARCHAR(255) NOT NULL,
    event_type VARCHAR(128) NOT NULL,
    processed_at TIMESTAMPTZ DEFAULT now(),
    response_status INTEGER,
    error_message TEXT,
    created_at TIMESTAMPTZ DEFAULT now(),
    UNIQUE(provider, store_id, external_event_id)
);
```

প্রসেস করার আগে যাচাই করুন: একই `external_event_id` ইতিমধ্যে প্রসেস করা হয়েছে কিনা। যদি হয়, তাহলে `200 OK` রিটার্ন করুন কিন্তু প্রসেস করবেন না।

### ১.৩ রেসপন্স টাইম আউট
ওয়েবহুক রিসিভারকে সর্বোচ্চ **২ সেকেন্ড** এর মধ্যে `200 OK` রিটার্ন করতে হবে। দীর্ঘসময় কার্যক্রম (লেজার এন্ট্রি, ইমেইল পাঠানো) ব্যাকগ্রাউন্ড জবে এনকিউ করুন, সরাসরি ওয়েবহুক হ্যান্ডলারের ভেতর 아닙니다।

**ভুল প্যাটার্ন (কখনও করবেন না):**
```typescript
// ❌ ভুল: ওয়েবহুকের ভেতর ইমেইল পাঠানো
await sendEmail(...); // এতে টাইমআউট হবে
return NextResponse.json({ received: true });
```

**সঠিক প্যাটার্ন:**
```typescript
// ✅ সঠিক: ডাটাবেসে লিখুন এবং ব্যাকগ্রাউন্ড জব এনকিউ করুন
await db.webhookEventLog.create({...});
await enqueueJob('process_webhook', { eventId, payload });
return NextResponse.json({ received: true });
```

### ১.৪ রietro tentativo (রietro attempt) ও ডেড লেটার কিউ
প্রোভাইডার থেকে 웹হুক ডেলিভারি ব্যর্থ হলে তারা রietro attempt করে। প্ল্যাটফর্মের পাশে:

1. প্রথম 어টেম্পটে ব্যর্থ হলে, প্রোভাইডারকে `5xx` রিটার্ন করুন (তाकि তারা রietro attempt करे)।
2. `4xx` রিটার্ন করুন শুধু যখন অনুরোধটি 본質ী τροめて ভুল (অবৈধ সিগনেচার, অনুপস্থিত প্যারামিটার)।
3. ব্যর্থ ওয়েবহুক একটি ডেড লেটার কিউ (ড বি টেবিল বা রেডিস কিউ) এ যাবে।
4. একটি ব্যাকগ্রাউন্ড জব প্রতিটি ৫ মিনিটে ডেড লেটার কিউ থেকে ব্যর্থ ওয়েবহুক রietro attempt করবে, সর্বোচ্চ ৫ বার।
5. ৫ বার ব্যর্থ হলে অফিস টিমকে অ্যালার্ট পাঠানো হবে।

### ১.৫ অর্ডারিং গ্যারান্টি (ক্রমাবর্তী প্রসেসিং)
একই অর্ডারের জন্য একাধিক ওয়েবহুক আসতে পারে (例如: `order.created`, `order.paid`, `order.fulfilled`)। প্ল্যাটফর্মকে বাধ্যতামূলকভাবে:

1. ইভেন্টের টাইমস্ট্যাম্প অনুযায়ী সাজানোর চেষ্টা করুন (যদি প্রোভাইডার পাঠায়)।
2. একই অর্ডারের কনকরেন্ট প্রসেসিং রোধ করতে ডिस्ट্রিবিউটেড লক ব্যবহার করুন (উদাহরণ: রেডিস লক, কি = `webhook:order:{external_order_id}`)।
3. পুরনো ইভেন্ট নতুন ইভেন্টকে ওভাররাইট করবেন না। স্ট্যাটাস ছোট হতে পারে (যেমন: `paid` এর পর `fulfilled` আসতে পারে, কিন্তু `fulfilled` এর পর `paid` আসলে উপেক্ষা করবেন)।

### ১.৬ এসএসএল/টিএলএস
প্রোভাইডার যেভাবে ওয়েবহুক পাঠায়, প্ল্যাটফর্মের ওয়েবহুক এন্ডপয়েন্ট অবশ্যই `https://` এ হোস্ট থাকতে হবে। স্বাক্ষরিত সার্টিফিকেট আবশ্যক। নিজস্ব-স্বাক্ষরিত সার্টিফিকেট প৯ রietro attempt বাধা দিতে পারে।

## ২. এপিআই নির্ভরযোগ্যতা ও ত্রুটিমুক্ত ক্রিয়াকলাপ

### ২.১ 인증 ও অনুমতি
প্রতিটি API অনুরোধে প্রমাণীকরণ হেডার থাকতে হবে:

- প্ল্যাটফর্ম API কী: `Authorization: Bearer <platform_api_key>`
- হম্যাক সাইনিং: `X-KD-Signature: <hmac_sha256_hex>`
- দোকান অ্যাক্সেস টোকেন: `Authorization: Bearer <store_access_token>`

অনুরোধ করা রিসোর্সের `company_id` অ্যাক্সেস করতে পারছে কিনা RLC প্রয়োগ করুন।

ভুল কোড গুলো:

- `403` — অনুমতি নেই
- `404` — রিসোর্স পাওয়া যায়নি
- `409` — সংঘর্ষ (একই এক্সটার্নাল অর্ডার আইডি)
- `422` — ব্যবসা নিয়ম লঙ্ঘন (অপর্যাপ্ত ব্যালেন্স)
- `429` — রেট লিমিট 오verage
- `500` — সার্ভার ত্রুটি

## ৩. রিয়েল-টাইম সিঙ্ক প্রক্রিয়া

### ৩.১ স্টোর → প্ল্যাটফর্ম (অর্ডার সিঙ্ক)
শপিফাই বা ও stories থেকে অর্ডার আসলে:

1. ওয়েবহুক রিসিভ → সিগনেচার যাচাই → আইডempootেন্সি চেক
2. অর্ডার ডাটাবেসে লিখা (`store_orders` টেবিল)
3. প্ল্যাটফর্মের পেমেন্ট লেজারে এন্ট্রি
4. মার্চ্যান্ট ড্যাশবোর্ডে রিয়াল-টাইম আপডেট (ওয়েব সকেট বা সার্ভার-সেন্ট ইভেন্ট)

### ৩.২ প্ল্যাটফর্ম → স্টোর (পেমেন্ট স্ট্যাটাস আপডেট)
প্ল্যাটফর্ম থেকে পেমেন্ট সফল হলে:

1. পেমেন্ট লেজার আপডেট
2. স্টোরের কলব্যাক URL এ `POST /kd-webhook/payment-updated` পাঠানো
3. স্টোরের ওrebroder স্ট্যাটাস আপডেট (যেমন: `pending` → `paid`)

スタور কলব্যাক ব্যর্থ হলে রietro attempt করুন (সর্বোচ্চ ৫ বার) এবং ডেড লেটার কিউতে রাখুন।

| API এরর রেট > ১% | হাই | অফিস teams → ইমেইল |
| ওয়েবহুক গড় রেসপন্স টাইম > ২ সেকেন্ড | মিডিয়াম | ইমেইল |
| ডেড লেটার কিউ > ১০ ব্যর্থ ইভেন্ট | হাই | অফিস teams → স্মার্টফোন |
| প্রোভাইডার সংযোগ ব্যর্থ | ক্রিটিকাল | অফিস teams → ফোন + ইমেইল |

### ৪.৩ লগিং
প্রতিটি ওয়েবহুক ও API কলের লিখুন:
- অনুরোধ আইডি (`request_id`)
- তালিকা (প্রোভাইডার, স্টোর আইডি, এন্ডপয়েন্ট)
- রেসপন্স স্ট্যাটাস কোড
- এরর মেসেজ (যদি থাকে)
- টাইমস্ট্যাম্প

সেন্ট্রি (Sentry) এ এরর রিপোর্ট করুন।
