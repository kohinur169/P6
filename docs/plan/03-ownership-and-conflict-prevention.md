# 03 - OWNERSHIP AND CONFLICT PREVENTION

This document guarantees that 16 separate chats never create the same thing twice.

## 1. Hard rules

- A step writes only inside its assigned directories, API namespaces, tables and
  migration range.
- A step never edits a shared registry owned by another step. It records a change
  request in its handoff document; the owner step applies it.
- Before creating any file, table, type, component or utility, the step searches the
  repository for an existing implementation. Reuse beats creation.
- Table names, route segments and component names are globally unique, not per step.
- Migration sequence numbers are reserved per step and never reused or renumbered.

## 7. Duplicate prevention checklist (run before every sub-step)

1. Search the repository for the planned file name.
2. Search for the planned table name in `migrations/**` and in
   `docs/plan/04-data-model-map.md`.
3. Search for the planned API route.
4. Search for an existing utility, type or Zod schema that already does the job.
5. Confirm the migration sequence number is inside the step range and unused.
6. Confirm no other step declared the same permission key or feature flag.

If any check fails, stop and resolve before writing code.

## 8. Git protocol

- Branch per step: `step/XX-short-name`, created from `main` after the previous
  step is tagged.
- Conventional commits, one per sub-step, message includes the sub-step id.
- Pull request to `main` with the handoff document linked. `main` is the
  integration branch and is always deployable.
- Tag `step-XX-done` after merge.
- No force push to `main`. No history rewrite of completed steps.
- A fix to an earlier step is a new commit on a `fix/<area>` branch with a
  handoff note, never a silent edit that breaks later assumptions.
